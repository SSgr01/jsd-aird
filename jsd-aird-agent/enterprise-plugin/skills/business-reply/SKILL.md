# 业务回复起草

先确定回复对象、沟通主题和用户希望达成的结果，读取相关原文及获授权业务记录。将已知事实、可以引用的承诺、待批准事项和待客户确认问题列清，再起草回复。默认清晰、专业、简洁；任务明确指定语气时依其要求。

价格、交期、性能和技术保证须有实际批准依据；没有依据时使用待确认表述，不能将内部推测改成对外保证。涉及异常或研发原因时保留不确定性，不能用假设代替已确认原因。草稿只保留对方有必要知道且用户可使用的信息。

客户需求变化场景，复用 customer-requirements 已核对的前后要求、确认状态和沟通目的；尚未核对且需要比较时才读取该技能，不重复整理已有依据。旧报价、旧交期或旧性能承诺须核对产品、数量、条件与有效期，不能自动套用到新要求。回复应围绕当前需要确认或推进的事项，说明已知内容，提出少量有决策目的的问题；不把内部分析表照搬给客户，不泄露无关配方、成本、内部评价或其他客户信息。

内部尚待核实的事项与对外草稿分开列出。可用“相关条件还需核实后确认”等真实表述，但不能编造“已经提交研发”“正在排产”“明日一定答复”等动作或时间。用户需要可直接使用的草稿时，关键缺口采用可理解的待确认措辞；若缺少回复对象或核心事实使草稿无法成立，明确指出必要缺口，不把未填占位符冒充完整回复。

交付可编辑回复草稿及少量影响发送的待确认项。只起草；用户未明确授权时不发送、不更新客户状态，也不声称对方已经收到或认可。
