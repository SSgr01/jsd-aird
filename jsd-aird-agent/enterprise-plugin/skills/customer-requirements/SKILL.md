# 客户需求整理与比较

先明确用户要提取需求、比较变化还是准备下一次沟通，以及希望本次沟通确认什么。简单提取不强制展开全部分析，用户只要回复草稿时按需读取 business-reply。

## 对齐原始要求与确认状态

固定客户、产品或样品、需求版本及沟通时间，先读取用户资料和获授权业务记录。按需通过 tool_search 发现 business_search/read/links，使用返回的固定 ref 与分页；客户、沟通、需求及项目仅沿真实关系展开。同名联系人或相似产品不能作为同一客户、要求或样品的证据。无权读取或未接通时说明限制，不当作没有记录。

逐项提取用途、应用基材、材料体系、性能指标、单位、方法与条件、数量、交期、验收和特殊资料要求，保留原话与位置。客户原话、结构化理解、内部判断分开；客户询问、提议、附条件要求、明确决定及公司批准承诺分别说明。不从联系人职称推断批准权限，不把最新一条消息自动当作已生效的新标准。

以同一对象和需求项对齐前后原文，列新增、明确撤回、值变化、条件变化及未再次提及。未提及不等于取消；最新版本号和更新时间不能证明具体变更。没有旧要求时整理当前要求与待核实基线，不编造差异。沟通原话相互冲突时并列来源并列待确认，不擅自选择一个覆盖另一个。

值、单位、方法或测试条件不相容时先说明原因，不直接判好坏。数值与单位换算使用 quantity_check 或可复核代码；“提升10%”“加快一些”等缺少基线、分母或具体日期时先确认口径，不自行设指标。

## 解释变化对业务意味着什么

对与任务有关的变化，连接“变了什么 → 依据是什么 → 对使用、验证或交付有什么含义 → 还需确认什么”，不要停留在字段差异。只展开有资料支撑的维度，不为了填满表格推测所有后果。

- 用途、基材或使用条件变化：说明已有验证的适用性需要逐项核对；未经技术依据不直接断言必须换配方，也不将全部历史结论一概作废。
- 性能、方法或验收条件变化：指出是否需要核对测试条件、补充验证或确认验收口径；数值相同不能掩盖方法或条件已变。
- 数量、交期或交付形式变化：指出需要内部核实的供货、排程、包装、报价和已批准承诺；没有库存、成本或排程依据不能保证供货、宣称涨价或确定延期。
- 文件或反馈变化：说明需要核对的产品、样品批次、文件版本和原始现象；客户抱怨不等于已确认质量原因或责任。

已知影响与合理但未证实的影响分开。客户没有说明的动机、预算、决策过程和采购意向不能作为事实。关联项目只证明归属，不能由此断言某个实验或任务必须重做；用户需要具体项目影响时按 project-diagnosis 方法核对相关对象和依赖。

## 准备有目的的沟通

按会改变验收、方案、报价或交付决定的问题排序，优先处理阻止下一步的关键歧义。每个重要问题说明为什么问、希望确认的事实以及不同答案会影响什么决策；能给出有依据的选项时给选项，不替客户选择。已在原文明确的信息直接复述确认或引用，避免重复索要。

客户需要确认的使用场景、验收口径、样品身份和需求取舍，与公司内部需研发、质量、生产或商务核实的可行性、标准、排程和授权分开。不能让客户替公司确认库存或生产能力，也不把尚未核实的内部假设写进对外问题。根据实际依赖建议先后顺序：例如先确认方法与基准，再由内部评估，最后提出可批准的方案，不默认所有沟通都要等内部核实完。

后续动作写明需取得的资料、判断或确认。已有责任人和期限引用实际记录；缺失时标待确认，建议角色不写成已分派，建议时间不写成承诺。仅凭客户未回复不能判断其拒绝或失去意向，不自行设置催办天数或声称已经催办。

## 交付

按用户范围给出需求摘要、变化的业务含义、客户问题及目的、内部核实事项和建议沟通顺序；复杂问题可用表格，不强制单句回复套用完整结构。关键判断就近引用真实原文和版本；明确哪些是事实、解释和待确认项。

需要回复时按 business-reply 起草清晰可编辑的内容，使用已核实事实和当前适用的批准承诺，未确认事项采用真实的待确认措辞。关键缺失字段采用固定专家的核验清单，公司特殊要求未知则标待确认。不虚构客户回复，不自行更新客户或需求记录，不对外发送或作出承诺。
