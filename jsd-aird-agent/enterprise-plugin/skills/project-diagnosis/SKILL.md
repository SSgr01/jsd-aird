# 项目进展与研发联动

先明确用户要了解的是状态、阻塞、下一步还是需求变化。简单状态查询只读取相关记录；分析项目进展、风险或影响时，才按下述方法展开，不机械地把每次回答做成全项目报告。

## 读取真实依据

用 business_search 查找项目，business_read 读取返回的固定修订；用 business_links 先发现可用关系，再分别展开该项目实际已有的阶段、任务、客户需求、资料和实验，按 next_offset 读完所需分页。按需用 tool_search 发现工具，重名时确认，不以相似名称冒充业务关联。搜索或关联结果已有完整正文时可复用；摘要和数量不能代替内容，缺正文时沿返回的 ref 读取。不编造工具参数、历史版本或对象 ID。

分析相关要求的原文、指标、方法条件、状态及版本；任务的目标、交付、阶段、责任人、计划日期和已记录依赖；实验的背景、方案、配方、工艺、样品及结果。资料只写“已完成”而没有交付证据时，不能直接视为客户指标已经验证。

项目的“资料”是业务资料，不是配方物料；资料数为零不能推出没有配方。需要实验全貌时优先用 section=record；局部问题可从概览定位，分析缺口前读共用字段、背景与方案，并读完相关分区及保存正文。即使样品数为零，背景也可能保留配方与历史版本锚点；沿明确的历史对象和版本读取，区分历史依据、方案和本次实测。资料有固定文献或文件身份时才按需读取其全文。无权读取、未接通或分页未读完均不能写成没有记录或已覆盖全项目。

## 对齐要求 任务与实验

围绕当前问题逐项建立“要求或目标 → 对应任务交付 → 实验或测试证据”的对应关系。先采用已保存对象关联、明确编号和正文中的确切引用；只同属一个项目不代表某实验验证了某要求，也不代表任务之间存在依赖。内容相似只能提出候选关系，写明待核实，不能伪装成正式关联或静默补建关系。

核对适用的要求版本、样品、指标、单位、方法、基材及测试条件；复用 customer-requirements 和 experiment-comparison 的专业方法，按需读取相应技能。数值核对使用可发现的 specification_compare、quantity_check 或可复核代码，不心算关键差异；工具只核对提交的输入，不能证明规格适用。缺少标准、条件或本次实测时不判达标。

按实际证据区分：已验证、已有可比结果但未满足、未验证、条件不相容而不可比，以及关联待核实。保留记录事实与分析判断的区别；这些分类用于分析，不改变业务状态，不等于正式质量放行。旧条件下的结果可能仍有参考价值，不能因为新要求出现就一概作废。

只有取得真实前后要求或明确变更原文时才列具体变化；当前版本号、更新时间和本轮未再次提及不能证明某项变化或取消。客户提议、待确认要求与已批准基线分开。没有旧版时可以分析当前要求的验证覆盖，但必须说明无法确认前后差异。

## 解释影响与卡点

对重要问题说明“哪条要求或哪项交付存在什么问题 → 依据是什么 → 影响哪个任务、实验或阶段 → 为什么影响 → 建议下一步”。明确引用起点与受影响对象的证据；仅内容推断的路径写成潜在影响和待核实关系。依赖方向、前置条件或因果依据缺失时不宣称必然阻塞，不把先后时间当作依赖。

重点检查与用户问题相关的情况：任务标为完成但交付或指标证据不足；实验做完但相关测试未记录；已有可比实测未满足目标；客户新要求与现有实验方法或条件不相容；同一关联对象的记录相互冲突。它们是检查方向，不能为了凑清单编造问题；“未记录结果”不能写成“没有做测试”，“未满足指标”不能直接归因为某种原料或某个人。

把真实状态、已逾期、预计风险、阻塞与未知分开。按目标影响、明确依赖及真实期限说明建议优先顺序；未提供计划、读取时点或排程依据时，不判确定延期、不算影响天数、不声称已求出关键路径。没有发现有证据的问题时如实说明分析范围和剩余不确定性，不强行制造卡点。

## 交付可执行建议

先回答当前项目最需要关注的判断，再按问题给出要求与证据覆盖、影响及建议，避免逐条复述状态。复杂问题可用表格列“问题、依据、受影响对象、影响路径、建议行动、待确认”，不要求简单问题套全表。关键判断就近引用实际读取的固定记录和版本，资料不足时指出具体缺哪份记录、哪种条件或哪条关联。

建议必须对准已发现的问题，例如核实任务交付、补齐某项测试条件、确认需求版本或核查候选依赖。责任人、截止日期和客户决定只引用已有记录；新增分工或期限只能作为明确标注的建议，不能写成承诺。与已有确定性业务规则相关的事项，引用或建议由相应业务流程处理，不用模型重建规则。

只读项目和任务，不改状态、不发通知；需要完整编辑进入已有业务页面。
